# Refactor data-model — follow-up: CRUD domain resources as JSON-LD POJOs

> Follow-up to [`refactor-data-model.md`](refactor-data-model.md). That plan's Phases 1–4 turned the **readable** layer into POJOs and its (reworked) **Phase 5** flipped the wire format to JSON-LD-first (fetchWrapper, mock, `data.json`, `setAcr`). This plan converts the remaining **CRUD domain resources** to the same POJO pattern — compacted & framed JSON-LD, raw JSON-LD GET/PUT, no `fetchWrapper`, no `DataFactory`/N3 Store / RDFJS dataset where the read/write pattern allows.
>
> **Phase structure (by read/write pattern, in this order):**
> 1. **GET only** → JSON-LD POJO, no DataFactory/N3
> 2. **GET and PUT** → JSON-LD POJO, no DataFactory/N3
> 3. **GET and PATCH** → keeps **SPARQL update** (quad machinery stays)
> 4. **DataInstance** → own plan — [refactor-data-instance.md](refactor-data-instance.md) (mixed PUT/PATCH/blob; write-side class is today unused in production — needs a scope decision)

## The target pattern (established — `crud/role.ts` is the completed template)

References: **`packages/data-model/src/crud/role.ts`** (the Phase 2 template), `src/grant.ts` + `grant-context.ts`, `src/application-registration.ts`, `src/data-authorization.ts`.

Per resource:

1. **Context** — registry style: keep it **inline in the module** (like `role.ts`'s `roleContext`); extract to a `*-context.ts` file at `src/` root only if it must be shared/exported (like `grant-context.ts`).
   - `id: '@id'`, `type: '@type'`
   - each property mapped to its full IRI
   - node references: `@type: '@id'`; arrays: `@container: '@set'`; reverse relations: `@reverse`
2. **`fromJsonLd(doc, iri)`** → `frameDoc(doc, context, iri)` (jsonld-utils) → plain data (array-coerced members, string literals; `?? []` / `?? ''` for absent keys). ⚠️ **jsonld.frame emits `null` (not `undefined`) for framed-but-absent properties** — optional fields must normalize with `?? undefined` (role/application-registration were safe via `?? []`/`?? ''`; the invitation + social-agent-registration conversions needed explicit `?? undefined` for `note`/`registeredAgent`/`hasAccessNeedGroup`/`reciprocalRegistration`)
3. **`loadX(iri, fetch)`** → `fromJsonLd(await fetchJsonLd(iri, fetch), iri)` — `fetchJsonLd` (jsonld-utils) is the shared raw JSON-LD GET (Accept header, throws on !ok). Like `putX`, the loader takes the raw **fetch**, not the factory (transport-oriented; callers pass `factory.fetch.raw`)
4. **`putX(data, fetch: WhatwgFetch)`** → `putJsonLd(data.id, fetch, withContext(context, data))` — **no per-module `toJsonLd` function**, `withContext` is called inline. `putJsonLd` (jsonld-utils) is the shared raw JSON-LD PUT (Content-Type, throws on !ok, extra headers pass through). Both `putX` and `loadX` take the raw **fetch**, not the factory (transport-oriented; factory methods pass `factory.fetch.raw`)
5. **`type: string[]` is required on the data** — captured from framing on read (read-only POJOs too — web-id-profile, client-id-document), written via compaction on write; the rdf:type quad comes from the data, not from special-casing

Drops: `DataFactory`/`Store` (n3), `CRUDResource`/`fetchDataset`/`linkedIris`, quad getters (`getOneMatchingQuad`/`getAllMatchingQuads`), `toDataset`/`fromDataset`/`toJsonLd` wrappers, `setTimestampsAndAgents` where fixtures have no timestamps.

## Phase 1 — GET only (JSON-LD, no DataFactory/N3)

Goal: every **read-only** path stops touching quads. `DataFactory`, `Store`, `fetchDataset`, `linkedIris`, quad getters disappear from the read modules.

1. **New shared JSON-LD listing helper — ✅ done** — `linkedIrisJsonLd(iri, fetch, property)` in `jsonld-utils.ts` (builds on `fetchJsonLd` + `frameDoc` with a `@type: '@id'` + `@container: '@set'` context; returns `[]` when the predicate is absent). Replaces `linkedIris` everywhere; the old `linkedIris` was **deleted** from `crud/resource.ts`. `storageIri` **✅ done** — reads the storage description as JSON-LD via new `findNodeIdByType(doc, typeIri, base?)` (expand + walk, the JSON-LD equivalent of `getOneMatchingQuad(dataset, null, RDF.type, SPACE.Storage)`). **Correction vs. first attempt**: framing at the description IRI was wrong — the Storage-typed node lives at the storage root's `@id` (e.g. `<https://alice-home.pod.docker/> a space:Storage.` in the fixture), not at the `.well-known/solid` URL; `findNodeIdByType` searches the whole document for the Storage-typed node like the old quad query did.
2. **Registry listing/find modules — ✅ done** — swap `linkedIris` for `linkedIrisJsonLd`: role-registry (`roles`/`containedIncludes`), authorization-registry (`getDataAuthorizationIris`), agent-registry (`applicationRegistrations`/`socialAgentRegistrations`/`socialAgentInvitations`), data-registry (`hasDataRegistration`). All pass `factory.fetch.raw`; the `find*` functions ride along (they iterate the converted generators/helpers).
3. **Leaf loads — ✅ all done** — `loadAgentRegistration` (**removed, not converted**): a plain agent registration is never loaded or created standalone — no `factory.crud.agentRegistration` method, zero callers, and registrations on the wire are always `ApplicationRegistration`/`SocialAgentRegistration` (read via their own modules). Removing it also dropped the `getDataGrantIris` fetch-fallback (unreachable: loaded data always carries `hasDataGrant`) and its `factory` param (`getDataGrantIris(data)` / `getGranted(data)` now; call sites updated across data-model, authorization-agent, components, tests). `loadSocialAgentRegistration` **✅ done** — JSON-LD read with inline context, `type` captured, `reciprocalRegistration` a plain `@type: '@id'` node ref thanks to the lazy-reciprocal change below. `loadSocialAgentInvitation` **✅ done** (whole module converted in Phase 2 §3 — read + write together). `loadRegistrySet` (**✅ done**) — exception to the `loadX(iri, fetch)` signature: keeps `(iri, factory)` because `RegistrySetData` carries the `factory` field for behavior consumers (`data-authorization.ts`); its write (`updateRegistrySet`) was **deleted** (zero callers) — registry-set creation is bootstrap-only (`components/Account.ts` TriG template), so `RegistrySetDataInput` and the factory's `registrySet(iri, data?)` input branch are gone too.
4. **application-registration (Design B — client ID document as source of truth) — ✅ done** — deleted the N3 `fromDataset`/`loadApplicationRegistration` from `crud/`; the registration document is now a **single-node** resource (`type`, `registeredAgent`, `hasDataGrant`). The denormalized agent-node fields (`name`/`logo`/`accessNeedGroup`/`hasAuthorizationCallbackEndpoint`, today copied from the client ID document and written onto the registered-agent node) are **dropped from both read and write**; consumers read them via `factory.readable.clientIdDocument(registration.registeredAgent)` instead. Components: `buildApplicationProfile` fetches the client ID doc (as `getUnregisteredApplication` already does — keep the `name!` assertion safe with error handling); `addApplicationRegistration` loses its clientIdDocument copy step + try/catch. Route reads through the root POJO (`fromJsonLd`); add `loadApplicationRegistration(iri, fetch)`.
5. **Already-POJO cleanup** — apply the cleanup recipe established with **web-id-profile / client-id-document (✅ done)**: drop `fromDataset`/`toDataset`/`toJsonLd` leftovers, inline the `compactNodeTo*` conversion into `fromJsonLd`, capture `type` from framing, add `loadX(iri, fetch)` via `fetchJsonLd`, and delegate the `factory.readable.*` methods to those loaders — removing the `fromJsonLd as xFromJsonLd` alias imports and the duplicated fetch blocks in base-factory. Done (**✅**): shape-tree-description, access-need, access-need-group, access-description (all now pure JSON-LD reads with `type` + `loadX(iri, fetch)`; access-need's `descriptionLanguages` uses the new **`documentValues(doc, iri, predicate)`** jsonld-utils helper — expand + recursive walk, replaces the `parseJsonld`/`getAllMatchingQuads` document-wide scan; shape-tree will need the same). Remaining: grant + data-authorization — **deferred to Phase 2**, their `toDataset`/`fromDataset` are consumed by the PUT paths (authorization.ts write, `storeDataGrant`) and the `pojo/*`/`readable/*` tests, so they cannot complete inside this GET-only phase (see Phase 2 items 4–5); shape-tree + access-description-set — genuinely quad-based reads (blank-node `references`, reverse-lookup `loadDescriptions`), own approach beyond this cleanup. `toStore` in jsonld-utils stays for Phase 3's SPARQL needs.
6. **Module unification — single file per data model — ✅ done** — merged the root POJO + `crud/` pair into one module (the root file survives; it is the read home and the public `export * as DataRegistration/ApplicationRegistration` surface):
   - `data-registration.ts` — moved `createDataRegistration(data, factory)` (container.create) in from `crud/data-registration.ts`, then deleted that file; added `loadDataRegistration(iri, fetch)`.
   - `application-registration.ts` — moved `createApplicationRegistration(data, factory)` in from `crud/application-registration.ts`, then deleted that file; the type lives in the module itself (drop the `./crud/application-registration` type import/re-export); kept `loadApplicationRegistration(iri, fetch)` (JSON-LD).
   - Fixed import sites: `crud/data-registry.ts`, `crud/agent-registry.ts`, `authorization-agent-factory.ts` (pass `factory.fetch.raw`), and `crud/index.ts` re-exports (point `createDataRegistration`/`createApplicationRegistration`/`loadApplicationRegistration` at the root modules — they are public API via `export * from './crud'`).
7. **Class infrastructure consolidation — ✅ done** — `src/readable/resource.ts` deleted: `ReadableResource` (the `fetchData()` subclass of `Resource`) moved into `src/resource.ts`; `data-instance.ts` re-pointed to `'./resource'`, `crud/resource.ts` unchanged (imports from the index). Then `src/readable/` removed entirely: its `index.ts` was a pure type re-export shim whose every alias (`WebIdProfileData`, `ClientIdDocumentData`, `ShapeTreeDescriptionData`, `AccessDescription*`, `AccessDescriptionSetData`, `DataRegistrationData`, `ApplicationRegistrationData`, `ShapeTreeData`/`ShapeTreeReference`, `AccessNeedData`, `AccessNeedGroupData`, `DataInstanceData`/`ChildInfo`, `GrantData`) was already exported by `src/index.ts`. The one unique export — legacy alias `DataGrant` (= `GrantData`) — had a single consumer, `authorization-agent.ts` `findGrantForResource(): Promise<DataGrant>`; switched it to `GrantData` and dropped the alias. Net public-API change: `DataGrant` name removed. `Resource`/`ReadableResource` were later deleted too: `DataInstance` (their last subclass) was made standalone — see the data-instance plan / classification table.

## Phase 2 — GET and PUT (JSON-LD, no DataFactory/N3)

Goal: full-resource replace (PUT) writes become raw JSON-LD PUT — no `CRUDResource.update()`, no `setTimestampsAndAgents` unless fixtures carry timestamps.

1. **role.ts — ✅ done** (`loadRole(iri, fetch)` / `putRole(data, fetch)` / `fromJsonLd` + inline `roleContext`; shared `fetchJsonLd`/`putJsonLd` helpers; `loadRole` takes the raw fetch like `putRole`; factory + consumers unchanged). This is the template.
2. **registry-set.ts** — **void** (write deleted in Phase 1 §3): registry set creation is bootstrap-only (TriG template in `components/Account.ts`), so there is no runtime write to convert.
3. **social-agent-invitation.ts — ✅ done** — `loadSocialAgentInvitation(iri, fetch)` + `putSocialAgentInvitation(data, fetch)`/`setRegisteredAgent(data, fetch, webId)` → raw JSON-LD PUT (`putJsonLd` + inline `invitationContext`). Context: `prefLabel`/`note` (literals), `capabilityUrl` (**`@type: '@id'`** — fixture `registry.trig` stores it as an IRI, the old `toDataset` wrote a literal), `registeredAgent` (`@id`). The write now also emits `a interop:SocialAgentInvitation` (via `type` captured from framing / injected by `addSocialAgentInvitation` with `[INTEROP.SocialAgentInvitation.value]`), fixing the previous type-less PUT. `toDataset`/`CRUDResource.update` dropped; callers (`agent-registry` listing + `addSocialAgentInvitation`, `InvitationHandler`) pass `factory.fetch.raw`/`sai.factory.fetch.raw`.
4. **data-authorization.ts write — ✅ done** — `authorization-agent/src/authorization.ts`: `DataAuthorization.toDataset` + wrapper PUT replaced with `withContext(dataAuthorizationContext, data)` + `putJsonLd` JSON-LD PUT (`If-None-Match: '*'` kept via the headers param). `replaceDataAuthorizationsForGrantee` (DELETE) stays raw.
5. **grant.ts / data-authorization.ts `toDataset` cleanup — ✅ done** — `toDataset`/`fromDataset` dropped from `grant.ts` + `data-authorization.ts` (production writes go through `toJsonLd`/`withContext` → `putJsonLd`); `pojo/*.test.ts` + `readable/*.test.ts` converted to the `toStore(X.toJsonLd(...))` quad-check recipe; the only remaining `toDataset`/`fromDataset` are the intentional Phase 3 SPARQL-path modules (shape-tree, agent-registration, social-agent-registration).
6. **`setAcr`** stays raw **turtle** PUT (ACL boundary — Phase 5 of the original plan).

## Phase 3 — GET and PATCH (SPARQL update stays)

Goal: the **incremental-patch** data models keep the SPARQL machinery (`container.ts`, `insertPatch`/`deletePatch`, DataFactory for patch quads). Their reads are already converted in Phase 1; this phase consolidates the write side.

1. **`container.ts`** — module functions are the quad-level SPARQL infra: `createContainer(iri, factory, dataset)` (PUT empty container + SPARQL PATCH into the description resource), `addStatement`/`removeStatement`/`replaceStatement` (PATCH via `insertPatch`/`deletePatch`), `applyPatch(containerIri, factory, sparqlUpdate, descriptionResourceIri?)` (HEAD + Link discovery unless the description IRI is passed), plus `setTimestampsAndAgents` (moved in from the deleted `crud/resource.ts`). **✅** The `CRUDContainer` class is **deleted** — production-dead once `createContainer` existed (zero callers; its tests were ported to the module functions: `crud/container.test.ts` now covers `replaceStatement`/`applyPatch`/`setTimestampsAndAgents`; `crud/resource.ts` + `crud/resoruce.test.ts` deleted). All 8 container creates (registries + registrations) go through `createContainer` (exported from `crud/index.ts`).
2. **agent-registration.ts** — `addDataGrant`/`removeDataGrant`/`removeAllDataGrants` stay SPARQL (`addStatement`/`removeStatement`).
3. **social-agent-registration.ts** — `updateReciprocal`, `setAccessNeedGroup`, `discoverAndUpdateReciprocal` stay SPARQL; `createSocialAgentRegistration` stays container.create.
4. **Registry creates + linking** — agent-registry (`createAgentRegistry`, `addApplicationRegistration`, `addSocialAgentRegistration`, `addSocialAgentInvitation`), data-registry (`createDataRegistry`, `createRegistration`), authorization-registry, grant-registry, role-registry (`createRoleRegistry`), data-registration, application-registration (writes moved into the unified root modules in Phase 1 §6) — stay on container.create (`createContainer`) + `addStatement` linking. **`createDataRegistration` — ✅ done**: build the dataset via **`jsonld.toRDF`** — `withContext(dataRegistrationContext, data)` → `toStore` (jsonld-utils) — instead of hand-building quads with `DataFactory` (the context already maps `type: '@type'`; the caller passes `contains: []`, which toRDF drops — server-managed); the container.create hand-off goes through `createContainer`. **`createApplicationRegistration` — ✅ done** (same `withContext` → `toStore` treatment; the derived `granted` field is dropped by toRDF since it is not in the context). Role's own `createRole`/`updateRole` are already JSON-LD; `deleteRole` is raw DELETE.
5. **Open question — resolved**: Community Solid Server **ignores the PUT body when creating containers**, so a content-bearing container can only be created via PUT-empty + SPARQL PATCH of the description resource — the `createContainer` flow. Raw JSON-LD PUT (like grants/roles, full doc + `Link` rel=type) only applies to non-container leaf resources (roles, grants, data authorizations, invitations — all already converted in Phase 2). **`createContainer` stays canonical for all 8 container creates; Phase 3 does not shrink.**
